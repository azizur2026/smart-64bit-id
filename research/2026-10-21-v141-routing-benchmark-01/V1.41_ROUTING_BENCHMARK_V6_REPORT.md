# SMART 64-bit ID v1.41 — Routing Microbenchmark (GCC v6)

**Date:** 2026-10-21
**Status:** Research results; reproducibility evidence included
**Scope:** Native C microbenchmark, not a database benchmark

## Research question

Under the tested workload, how does extracting the Engine field from a SMART 64-bit ID and routing by `Engine % shard_count` compare with direct full-ID modulo and a full-ID hash-table lookup?

This is a narrow microbenchmark. It does not establish that SMART routing is universally faster, nor does it establish PostgreSQL or end-to-end application performance.

## Tested methods

- **SMART Engine routing:** extract Engine using `(ID >> 29) & 0x1FFFFF`, then calculate `Engine % shard_count`.
- **Direct ID modulo:** calculate `ID % shard_count`. This is a different routing rule, so its route checksum is expected to differ.
- **Full-ID hash lookup:** hash the full ID, perform a linear-probing table lookup to retrieve Engine, then calculate `Engine % shard_count`.

The SMART and hash-lookup methods are expected to agree on routing results. Direct ID modulo is not semantically equivalent to Engine-based routing.

## Workload and procedure

- 524,288 generated IDs.
- Engine values drawn from a range of 131,072; each Engine occurs four times.
- Shard counts: 50,021 and 100,003.
- Ten original runs, with seven timing samples per method and shard count per run.
- Method order rotated to reduce fixed ordering effects.
- Benchmark pinned to CPU 2.
- Timing uses `CLOCK_MONOTONIC_RAW`.
- Setup and validation are excluded from timed sections.
- Hash lookup table: 1,048,576 entries (16 MiB).
- Native scalar compilation flags: `-O3 -fno-tree-vectorize -fno-tree-slp-vectorize -march=native -Wall -Wextra -Werror`.

## Validation

The benchmark's recorded validation checks include ID uniqueness, Engine extraction, hash-table lookup, and per-ID routing comparisons. The recorded SMART and hash-lookup route checksums match; the direct-ID-modulo checksum differs as expected because it implements a different routing rule.

The run outputs, stderr files, start/end metadata, exit-status files, and per-run artifact hash files should be retained alongside the summary. A successful process exit alone is not proof of every possible correctness property.

## Interpretation and limitations

In this specific test, SMART Engine extraction followed by Engine modulo took less measured time per ID than either direct ID modulo or full-ID hash lookup.

This is **not** a comparison of equivalent routing semantics for all three methods: direct ID modulo routes by the entire ID and intentionally produces different results. The hash-lookup method includes hashing and table lookup, whereas SMART routing extracts Engine directly from the encoded ID. The result therefore measures these concrete implementations, not a universal cost of “conventional sharding.”

The test does not measure network, disk, database query planning, index maintenance, concurrent load, rebalancing, or application-level throughput and latency. PostgreSQL has not been benchmarked as part of this result.

## Conclusion

For this particular native microbenchmark, direct extraction of the Engine field and modulo routing measured approximately 3.09–3.12 ns/ID in the original ten-run summary. The observed ratios favor SMART Engine routing over the two tested alternatives, but the comparison is implementation- and workload-specific. Broader performance claims require semantically controlled routing comparisons and separate application/database benchmarks.
