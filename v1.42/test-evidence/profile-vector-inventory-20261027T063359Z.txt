254: This code implements the retention rule in `SPECIFICATION.md` §10.3 and the per-profile retention rule in §10.4. It applies when a retired record cannot be produced where the retaining profile requires it, or when a required coordinate-consumption tombstone is absent. It does not apply to the treatment of another profile's retired records, which is not an obligation of v1.42.
256: ### 7.4 S64-E016 and S64-E018 precedence
258: When an allocation is attempted at a coordinate that has been retired, `S64-E016` applies, not `S64-E018`. The coordinate-permanence rule governs retired coordinates; the Local non-reuse rule applies to coordinates that have been allocated and are not retired. This precedence is stated normatively in §4.5.
260: ### 7.5 S64-E018–S64-E023 (allocation)
262: These codes make explicit the allocation invariants stated normatively in `SPECIFICATION.md` §7 and §6. `S64-E019` and `S64-E020` are registry-only in the sense that the specification states the invariants but does not cite these codes. `S64-E021` is the diagnostic code when allocation safety cannot be established and no more specific condition applies, except where `FAIL_HARD` is required. An implementation MAY use these codes to report the corresponding condition and SHOULD do so where the condition is diagnosable.
264: `S64-E022 ENGINE_EXHAUSTED` is distinct from `S64-E008 ALLOCATION_NOT_FOUND`. `S64-E022` concerns the allocator's exhausted Local namespace and a safely reserved forward rollover target. `S64-E008` concerns the authoritative registry relative to a specific coordinate.
266: `S64-E021 ALLOCATION_SAFETY_UNESTABLISHED` matches the invariant in `SPECIFICATION.md` §7: if an implementation cannot establish safe uniqueness and non-reuse, allocation MUST fail.
268: ### 7.6 S64-E024 RETIREMENT_REQUIRED and S64-E025 RETIRED_IDENTIFIER_OPERATION
270: `S64-E024` applies only when a specific operation step requires the source identifier to have already been retired and the source remains active. It MUST NOT be applied merely because a successor is being allocated before retirement: `SPECIFICATION.md` §10.5 intentionally allocates the successor first and then performs an atomic activation/retirement transition.
272: `S64-E025` applies when an operation not permitted on a retired identifier is attempted on one whose record is retired.
274: ### 7.7 S64-E026 PROFILE_BOUNDARY_VIOLATION
276: This code covers the cases in `SPECIFICATION.md` §13.4 where an implementation would accept, reinterpret, convert, rewrite, truncate, or mask an identifier belonging to another profile. It is distinct from `S64-E002 UNSUPPORTED_PROFILE`, which applies when the profile itself is not supported; `S64-E026` applies when the operation would cross a profile boundary.
278: ### 7.8 S64-E027 FIELD_EXTRACTION_INVALID and S64-E028 SERIALIZATION_NONCANONICAL
280: These are conformance-category codes, used to report implementation defects rather than input defects. `FIELD_EXTRACTION_INVALID` applies when extraction is inconsistent with the bit positions defined for the identified profile. `SERIALIZATION_NONCANONICAL` applies when binary serialization or deserialization does not preserve all 64 bits in canonical form where canonical interoperability is required.
282: ### 7.9 S64-E029 ENGINE_ID_SPACE_EXHAUSTED
286: `S64-E029` is terminal for the current allocation attempt and MUST NOT wrap around to lower Engine IDs. It is distinct from `S64-E022 ENGINE_EXHAUSTED`, which applies only when a safe forward target has been found and reserved. If authoritative state or reservation safety cannot be established, report the applicable authority or safety failure instead. Expansion of the Engine ID space requires a new profile or a separately defined Class assignment; existing identifiers are not renumbered.
288: ### 7.10 S64-E009 ALLOCATION_CONFLICT
290: Exactly one canonical allocation record MUST exist for each Engine + Local coordinate ever allocated. More than one canonical allocation record for the same coordinate is `S64-E009 ALLOCATION_CONFLICT`, regardless of whether the duplicate records have the same or different lifecycle States.
